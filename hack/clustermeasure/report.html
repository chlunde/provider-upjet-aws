The provider pod's 380 MB

Sixty arms, nine rounds, measured through the cgroup Kubernetes actually bills. A kernel setting nobody had looked at. 26 MB of embedded data parsed to read 0.35 MB of it. Eight regular expressions compiled 269 times. An AWS client rebuilt, with a fresh connection pool, on every single reconcile. 382 MiB became 76.6.

Huge pages off 205MiB One environment variable. No code change, no upstream change.
Config build 13.7s → 1.1s Per-family include list; pod Ready 17 s → 4 s

Everything measured about this provider's memory so far came from /proc/self/smaps_rollup and runtime.MemStats, read inside a process that links the same packages a family provider links. Those numbers are correct about the Go heap. They are not the number a pod is charged.

So: build cmd/provider/s3 from the tree, put it in a kind cluster, point it at LocalStack, give it fifty real Bucket resources to reconcile, and read the container's memory.current. One binary throughout — every arm is an environment variable, so nothing about what is linked changes between them.

02 / The finding

Huge pages, not the Go heap, decide what the pod reports

The largest single lever in the table is not a patch. Turning transparent huge pages off for the process — GODEBUG=disablethp=1 — takes steady state from 385 MiB to 205 MiB. Setting the node to transparent_hugepage=madvise and re-running the untouched baseline lands on 201 MiB. Two independent routes to the same −47%, which is the check that the effect is really THP.

The kernel counters say why. When Go's scavenger returns a span it calls MADV_DONTNEED on a range that usually sits inside a 2 MiB huge page. The kernel unmaps the sub-range — which is what the process's own smaps reports — and puts the compound page on a deferred-split queue, to be broken up and freed only under memory pressure. Until that happens the whole 2 MiB is still charged to the container.

03 / Two corrections

What the process-level harness could not see

A one-shot FreeOSMemory() is worth less than half of what it looks like

Called once after the two config.GetProvider builds, it drops the process's own anonymous memory by 219 MiB — and the pod's bill by 120 MiB, for the reason above. By steady state it is worth nothing at all: 389.9 MiB against a 382–389 MiB baseline. It shortens the window after startup and changes no steady-state number.

smaps is not a proxy for what a pod is charged

The two baseline runs, first and last of nine, differ by 175 MiB in smaps Anonymous (379.1 against 203.8) and by 6.5 MiB in memory.current (382.2 against 388.7). The process-level view is the unstable one. The cgroup view is the reproducible one.

Why this matters for the earlier work

Every figure in the existing footprint analysis is a smaps or MemStats reading. They are right about the heap, and they are not predictive of the metric anyone alerts on — which is the metric the whole investigation set out to explain.

04 / The startup win

Confirmed on a pod, and it holds at scale

Filtering upjet's include lists to the family's own resources cuts the two provider builds from 13.7 s to 1.13 s and the configured set from 1,029 resources to 25. The pod reaches Ready in 4 s instead of 17, or 2 s with GOMEMLIMIT also set. Fifty buckets reconcile identically under the filter: same 100 s to all-Ready, no panic, no missing controller.

It is also worth more in memory than the process-level harness suggested — that harness built the provider and exited, while a pod keeps 1,029 resource configurations live for its whole life:

05 / Round two

26 MB parsed at every start to keep 0.35 MB

With huge pages out of the way, the remaining number is the arena's high-water mark from startup — a heap profile of a steady-state pod puts the live object graph at just 72.6 MiB, against 181 MiB of resident arena and 28.7 MiB of goroutine stacks. So the lever is the peak, and the peak is two whole-file parses.

Reading what consumes them (upjet pkg/config/provider.go:376-458): at line 436 the JSON-derived schema is thrown away and replaced with the Go schema for every Terraform Plugin SDK resource — 960 of the 1,029 this provider configures. Only 69 Plugin Framework resources genuinely need it. Another 654 resources in the file are unmarshalled, converted, and dropped by the include list.

Trimming both files to what is actually read — 19.0 → 0.5 MB and 7.8 → 2.8 MB, still configuring all 1,029 resources — halves the startup peak, 380 → 175 MiB. The provider stops allocating more during startup than it holds afterwards.

Two things this is not. It is not a startup-time fix: 13.61 s becomes 12.96 s, because the 13 seconds are SchemaFunc() materialisation, which is what the family filter removes. And it is not shippable as written — cmd/generator embeds the same files and needs them whole, so it has to become a build artifact selected by tag.

What blocked the metadata half

The first attempt panicked at startup: config/cluster/apigatewayv2/config.go:50 runs r.MetaResource.Examples[0].SetPathValue("lifecycle", nil). The running provider parses 2.9 MB of documentation example manifests on every start so that a configurator can edit one of them. 368 of 1,676 resources have such a configurator — which is why the metadata only gets to 2.8 MB here instead of 0.3.

While there is slack the deferred-split charge is reclaimable: at 512Mi and 400Mi the huge-page arm pressed exactly to its limit, tripped one reclaim event and survived. Below the startup peak nothing saves it — and note that turning huge pages off does not help there either. Both arms die identically at 300Mi, because the Go runtime has no idea what the cgroup limit is. GOMEMLIMIT is what tells it; disablethp lowers what gets charged, only GOMEMLIMIT makes the runtime back off.

But the lowest steady figure belongs to filter + disablethp alone, at 142.4 MiB — below the all-in-one's 165 — because GOMEMLIMIT makes the scavenger target the limit rather than minimum footprint. The two goals pull apart: chase the metric and you want the filter without the limit; chase the smallest schedulable pod and you want all four, because that arm peaks at 187 MiB instead of 349.

Two more levers fell out of the same profile. GOGC=25 is worth −129 MiB of peak for +3.5 s — and its shippable form is debug.SetGCPercent(25) around the two provider builds, so the cost is paid once rather than forever. And the shipped default --max-reconcile-rate=100 spawns 6,278 goroutines, 28.7 MiB of stacks; at =10 the same workload runs 1,500 goroutines and 7 MiB.

One thing that did not work: turning down startup concurrency. GOMAXPROCS=2 makes the peak slightly worse (438 against 395). There is nothing concurrent to throttle — the two provider builds are sequential and the controllers start after the peak.

08 / Rounds three and four

The profile's top three moved nothing. Eight regexes moved 8 MiB.

With huge pages, the filter and the trim applied, steady state sat at 119 MiB. An alloc_space profile named three obvious culprits, so all three were implemented: upjet's config.matches recompiling every include-list pattern (575 MB, 32% of all allocation), clearing SchemaFunc so the schema stops being rebuilt on every Observe, and --poll-state-metric at 30 s instead of 5.

The result worth keeping

Every memory delta is inside noise. Footprint is live heap × (1 + GOGC/100) plus stacks, GC metadata and fragmentation — garbage the collector keeps up with never becomes resident. An alloc_space profile ranks what to fix for speed; inuse_space ranks what to fix for footprint. The regex patch is still a 2.7× startup win (and −5.5 s on an unfiltered provider), and clearing SchemaFunc is a correctness fix. Neither is a memory fix.

So the target became live heap, whose largest addressable item was 7–11 MiB of retained compiled regexes. They turned out to be the AWS SDK's partition region matchers: every generated service/*/internal/endpoints package compiles the same eight patterns at init, byte-identical in 60 of 60 packages sampled. A provider linking 269 services compiles 2,152 regexes to represent 8.

They were hoisted into internal/endpoints/v2 — which every one of those files already imports, so the change adds no dependency edge. 2,144 calls removed across 268 of 268 files; the binary grew 131 KB.

That is also the second half of a correction: round 1 said per-family linking of the fork could not move the pod metric because the code it removes is file-backed. An unlinked service package runs no init, so it removes this too.

Where the last 56 MiB is

Of the live heap that remains, ~14 MiB is Scheme.AddKnownTypeWithName plus conversion funcs and the RESTMapper for all 8,488 GVKs, and ~6 MiB is reflect.compiledTypelinks and friends. Both exist only because a single-family binary links every API group. Per-family API packages are the single largest remaining item, worth ~20 MiB of live heap — about 25 MiB of pod memory at GOGC=25, which is what would put steady state in the mid-80s. Nothing else measured gets under 100.

The method note

alloc_space ranks what to fix for speed; inuse_space ranks what to fix for footprint — and they disagree. The three largest allocation sites (575 MB of regex compilation, 168 MB per 3.3 min of schema deep-copying, 49 MB of schema rebuilds) moved the pod metric by nothing: garbage the collector keeps up with never becomes resident. The three largest retained structures moved it by 90 MiB.

Two corrections came out of these rounds. Per-family linking needs both generated registries trimmed — awsclient_gen.go imports the SDK clients, and Go initialises every imported package whether or not a symbol is reachable, so “accessors do not root at link time” is true of text and false of init. And init is 18.6 MiB of a stock provider’s live heap. The second: memoising the implied cty type, which looked like a 16 MiB win, moved nothing — that memory is in-flight reconcile state, not per-resource retention.

All of it verified on the fully-patched binary: 500 resources created, a second kind reconciled with LocalStack independently confirming the change reached the API, and deletion removing both the managed resource and the bucket.

10 / What to do

Ranked by measured effect on the pod metric

  1. Set GODEBUG=disablethp=1 In the provider's DeploymentRuntimeConfig, or run nodes with transparent_hugepage=madvise. A no-op where THP is already madvise, so check your nodes first. −180 MiB · −47% · no code change
  2. Set GOMEMLIMIT — for survival, not for the metric Without it the provider is OOM-killed at any limit below its startup peak; with it, it runs at 300Mi. Apply it after the trim, or it costs 40 s of startup. OOMKilled → 0 restarts at 300Mi
  3. Filter the resource map before converting it upjet converts all 1,683 schemas before consulting any include list, then discards what is not kept. ~15 lines, no build step, no second copy of the blobs. −91.5 MiB of startup peak
  4. Stop rebuilding the AWS client every reconcile Each Connect constructs a fresh client with its own HTTPClient, so every reconcile starts with an empty connection pool. −59.6 MiB at 500 managed resources
  5. Strip the informer cache managedFields and the last-applied annotation, dropped on the way in — the mechanism the CRD cache already uses. −59 KB per managed resource
  6. Share the AWS SDK's partition regexes Hoist the eight partition matchers into internal/endpoints/v2, which every service endpoint file already imports. Codegen-only, upstream, no new dependency. −8.6 MiB on the pod · 2,152 → 8 compiles
  7. Ship the per-family include list The largest single cut to the steady-state number, and it takes startup with it. Needs the elbv2 imperative ShortGroup override handled; webhook setup still unverified. −20% steady · 13.6 s → 0.5 s
  8. Stop parsing what is never read Downstream-only for the schema. The metadata needs ~368 configurators guarded first — they edit documentation at runtime. startup peak 380 → 175 MiB
  9. Reconsider --max-reconcile-rate=100 as a default A family provider rarely needs 100 concurrent reconciles, and the default is not free. ~22 MiB of goroutine stacks
  10. Per-family API packages — the last big one The 8,488-GVK scheme, its conversion funcs and RESTMapper, plus the reflect metadata that follows. Real codegen work, and the only measured path under 100 MiB. ~20 MiB of live heap · ~25 MiB of pod memory
  11. Do not ship a one-shot FreeOSMemory() Already retracted; the cluster confirms it changes no steady-state number. 0 MiB at steady state

11 / Scope

What this does not cover

  • One node, arm64, one family, LocalStack rather than AWS, n=1 per arm (n=2 for baseline), 8 minutes of steady state per arm.
  • No webhooks, no leader election, no Crossplane package manager, no cross-family reference resolution exercised.
  • --skip-default-tags is set, and a tag shim stands in for an S3 Control call LocalStack fails, so the tag path is lighter than production.
  • The binary is mounted by hostPath, so its 278–313 MiB of resident text is not charged to the pod here. Read every figure as the anonymous half; a pod faulting those pages from its own image layer carries up to ~300 MiB more until they age onto the inactive-file list.
